# Deploying VytalAI — step by step

Architecture: **Frontend** (Vercel/Netlify, static) → **Backend** (Render, Docker) → **MongoDB Atlas**,
plus an **ElevenLabs** agent that calls the backend's webhook after each voice registration.

Do the steps in this order — each one produces a value the next one needs.

| # | You create | You get (write it down) |
|---|---|---|
| 1 | MongoDB Atlas cluster | `MONGO_URI` |
| 2 | Backend on Render | `https://<api>.onrender.com` |
| 3 | Frontend on Vercel | `https://<app>.vercel.app` |
| 4 | Tell backend about the frontend | `FRONTEND_ORIGINS` set |
| 5 | ElevenLabs agent | `AGENT_ID`, webhook secret |

---

## 0. Test locally first (15 min, strongly recommended)

```bash
docker compose up -d mongo          # or install MongoDB yourself
cd backend && python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt && cp .env.example .env && python main.py
# new terminal
cd frontend && npm install && cp .env.example .env && npm run dev
```
Open http://localhost:5173/login → **Admin** tab → `admin@vytalai.com` / `Admin@VytalAI123`.
Then open `/register` → **Manual Sign Up**, create a patient, and check it appears in the admin dashboard.
Run `cd backend && pip install -r requirements-dev.txt && pytest -q` to run the API tests.

## 1. MongoDB Atlas (database)

1. Create a free account at mongodb.com/atlas → **Create a cluster** (M0 free is fine to start).
2. **Database Access** → Add database user (username + strong password; save them).
3. **Network Access** → Add IP address. Render's outbound IPs change on lower plans, so for a first deploy use
   `0.0.0.0/0` (allow from anywhere) — the database is still protected by the user/password. Tighten later.
4. **Connect → Drivers** → copy the connection string:
   `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?retryWrites=true&w=majority`
   Replace `<user>` / `<password>` (URL-encode special characters in the password, e.g. `@` → `%40`).
   This is your **`MONGO_URI`**.

> Reusing data from the original project? Set `DB_NAME=medical_records`. Default is `vytalai`.

---

## 2. Backend on Render

1. Push this folder to a GitHub repo (e.g. `VytalAI`) — `.env` files are git-ignored, never commit secrets.
2. Render dashboard → **New → Blueprint** → pick the repo. It reads `render.yaml` and creates the `vytalai-api` service.
   (Manual alternative: New → Web Service → Runtime **Docker**, Root Directory `backend`, Health Check Path `/health`.)
3. Fill in the environment variables Render asks for:

   | Variable | Value |
   |---|---|
   | `ENVIRONMENT` | `production` (preset) |
   | `MONGO_URI` | from step 1 |
   | `JWT_SECRET_KEY` | auto-generated by the blueprint (or run `python -c "import secrets;print(secrets.token_urlsafe(48))"`) |
   | `ADMIN_EMAIL` | your real admin email |
   | `ADMIN_PASSWORD` | a strong password — **must not** be the default or the server won't start |
   | `FRONTEND_ORIGINS` | leave a placeholder now; set in step 4 |
   | `ELEVENLABS_WEBHOOK_SECRET` | set in step 5 |
   | `DOCTOR_SIGNUP_CODE` | optional invite code doctors must enter |

4. Deploy. When live, open `https://<api>.onrender.com/health` → `{"status":"ok"}`.
   Your backend URL is `https://<api>.onrender.com` (no trailing slash).

> **Free tiers sleep** after inactivity and take ~30–60 s to wake; a sleeping backend can make the first
> ElevenLabs webhook time out (it retries, but patients may wait). Use an always-on plan for real use.
> Railway, Fly.io and Google Cloud Run also work with the same `Dockerfile` — set the same variables.

---

## 3. Frontend on Vercel

1. vercel.com → **Add New → Project** → import the same GitHub repo.
2. **Root Directory:** `frontend` · Framework preset: **Vite** (build `npm run build`, output `dist`).
3. **Environment Variables:**
   - `VITE_API_BASE_URL` = `https://<api>.onrender.com` (https, no trailing slash)
   - `VITE_ELEVENLABS_AGENT_ID` = your agent id (step 5; can be added later)
4. Deploy → note the URL, e.g. `https://vytalai.vercel.app`.

Netlify instead: Base directory `frontend`, build `npm run build`, publish `frontend/dist`, same two variables
(`public/_redirects` is already included for routing).

> `VITE_*` variables are baked in at build time — after changing one, **redeploy** the frontend.

---

## 4. Allow the frontend to call the backend (CORS)

In Render → `vytalai-api` → Environment, set
`FRONTEND_ORIGINS=https://vytalai.vercel.app` (comma-separate multiple, e.g. add your custom domain; no trailing slashes).
Save → the service redeploys. Without this the browser blocks every request ("CORS error").

---

## 5. ElevenLabs voice agent

1. In ElevenLabs → **Agents** (Conversational AI) → create an agent that greets the patient and collects their details.
2. **Analysis → Data collection:** add these fields — the **names must match exactly**:

   `Name`, `Age`, `Gender`, `Contact`, `Address`, `Reason`, `Previous Medical History`, `Emergency Contact`, `Appointment Preference`

   (Give each a short description like "Patient's full name"; `Contact` = 10-digit phone number — it becomes their first password.)
3. **Webhook:** in ElevenLabs' Conversational AI **settings** enable the **post-call webhook** (transcription) and set the URL to
   `https://<api>.onrender.com/webhook/elevenlabs`. Choose HMAC authentication, copy the generated **secret**, and put it in
   Render as `ELEVENLABS_WEBHOOK_SECRET` (the service redeploys). The backend then rejects unsigned requests.
4. Copy the agent id and set it as `VITE_ELEVENLABS_AGENT_ID` in Vercel → **redeploy** the frontend.
5. **Allow the widget on your site:** if your agent has an allowlist (Security tab), add your frontend domain.

**How a voice registration reaches only the right browser:** the page generates a random session id and passes it to the
widget as the dynamic variable `session_id`; ElevenLabs echoes it back in the webhook, and the backend delivers the result
only to that browser (plus admins). Verify this in step 6 — if after a test call the page never shows the review form but the patient
*does* appear in the admin dashboard, ElevenLabs isn't echoing `session_id`: check the agent/webhook settings, or just
let patients use **Manual Sign Up**, which is independent of it.

## 6. Smoke test (production)

- [ ] `https://<api>.onrender.com/health` → ok; `/docs` returns 404 (hidden in production, by design)
- [ ] Frontend loads; refreshing on `/login` does not 404
- [ ] Admin login works; header shows green **Live** dot (WebSocket connected over `wss://`)
- [ ] `/register` → Manual Sign Up creates a patient; it shows in admin → **Pending**
- [ ] Doctor signs up at `/signup`; admin assigns a patient to them; doctor's dashboard updates
- [ ] Doctor adds a prescription / changes status; patient logs in (forced password change), sees it
- [ ] Voice test call: result appears on the page and in the admin dashboard
- [ ] Backend logs show no `Webhook rejected` / CORS errors

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Backend exits at boot: "Insecure production configuration" | Set a real `JWT_SECRET_KEY` (32+ chars), change `ADMIN_PASSWORD`, use Atlas not localhost |
| Browser console: CORS error | `FRONTEND_ORIGINS` missing/typo; must be the exact `https://…` origin, no trailing slash |
| Frontend calls `localhost:8000` | `VITE_API_BASE_URL` not set at build time → set it and redeploy |
| Login says "Cannot reach the VytalAI server" | Backend asleep/down, wrong URL, or `http://` page calling `https://` mixed content |
| "Live" dot never turns green | Token expired (log in again) or backend asleep; WebSocket needs `https`→`wss` (automatic) |
| Webhook 401 in logs | Secret mismatch between ElevenLabs and `ELEVENLABS_WEBHOOK_SECRET` |
| Webhook 200 but no patient | Data-collection field names don't match exactly (see step 5.2) |
| Atlas: "bad auth" / timeout | Wrong user/password in `MONGO_URI` (URL-encode symbols) or IP not allowed in Network Access |
| Old `…@patient.vocare` accounts | Still work with their stored email; only newly generated usernames use `@patient.vytalai` |

## Before real patient data

This is a solid project-grade app, not a certified medical system. Before storing real health information:
add login rate-limiting/lockout, move to an always-on paid backend + Atlas tier with backups and encryption policies,
review applicable regulations (e.g. India's DPDP Act, HIPAA if you serve US patients), consider replacing the
phone-number temporary password with an SMS/email one-time link, and get a security review.
